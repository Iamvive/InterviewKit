The 5 Manifest Launch Modes

standard

Default

Unconditionally creates a brand new instance and pushes it onto the task stack every time.

• Multiple instances allowed in same and different tasks.
• onNewIntent() is NEVER called.
• Ideal for product details, forms, standard pages.

singleTop

Top-Only Reuse

Reuses instance ONLY if it is already sitting at the top of the stack. Otherwise creates a new one.

• Reused at top: onPause() → onNewIntent() → onResume().
• Avoids duplicate screens when spam-clicking.
• Ideal for search screens, chat messaging targets.

singleTask

Clear-Top Anchor

At most ONE instance per task. If it exists, brings it to front and destroys all activities above it.

• Invokes onNewIntent() → onRestart() → onResume().
• Creates new task if launched with different taskAffinity.
• Ideal for Home/Dashboard, deep-link landing pages.

singleInstance

Complete Isolation

Runs in its own exclusive task. No other Activity can ever join its task.

• Launching any other Activity forces it into a separate task.
• Only 1 instance exists system-wide.
• Ideal for Incoming Call screen, Alarm ringing, Launcher.

singleInstancePerTask

API 31+ (Android 12)

A modern hybrid: Can have multiple instances across the system, but each instance must be the solitary root of its own Task.

• When combined with FLAG_ACTIVITY_MULTIPLE_TASK, always opens a fresh independent window.
• Built specifically for multi-window, tablets, and foldable devices (e.g. multi-document editing).

The Critical onNewIntent() Code Trap

When an Activity is reused (in singleTop, singleTask, or singleInstance), calling getIntent() will STILL RETURN THE OLD ORIGINAL INTENT unless you manually update it!

class ProductActivity : ComponentActivity() { override fun onCreate(savedInstanceState: Bundle?) { super.onCreate(savedInstanceState) val id = intent.getStringExtra("ID") // Reads initial intent } override fun onNewIntent(newIntent: Intent) { super.onNewIntent(newIntent) // 🚨 CRITICAL SENIOR INTERVIEW REQUIREMENT: // You MUST call setIntent(newIntent), otherwise any helper function or // ViewModel calling getIntent() will receive stale, outdated extras! setIntent(newIntent) val updatedId = newIntent.getStringExtra("ID") updateUi(updatedId) } }
Interview Gotcha: If you pass extras into a reused Activity and observe that your background repository or analytics still logs the old data, 99% of the time it is because the developer forgot setIntent(newIntent)!

Task Affinity & Production Architecture: The Chucker Case Study

Concept Mental Model What It Controls
taskAffinity "WHERE it lives" Which Task / Window group the Activity belongs to (Default: packageName).
launchMode "HOW it behaves" Instance creation rules (new vs reused) inside that Task.

Why Chucker Uses taskAffinity + singleTask:

<!-- Inside Chucker Library Manifest --> <activity android:name="com.chuckerteam.chucker.internal.ui.MainActivity" android:launchMode="singleTask" android:taskAffinity="com.chuckerteam.chucker.task" />
1. Custom taskAffinity: Prevents Chucker from hijacking the host app's back stack (e.g. your Checkout flow). Chucker gets its own independent Recent Apps card.
2. singleTask: Clicking multiple HTTP traffic notifications reuses the same Chucker window via onNewIntent() instead of stacking duplicate screens.

Launcher Intent Filters: What Happens & Why

<intent-filter> <action android:name="android.intent.action.MAIN" /> <category android:name="android.intent.category.LAUNCHER" /> </intent-filter>
Scenario What Happens Why Under the Hood
0 Activities have filter App installs, but NO icon in App Drawer. Launcher queries PackageManager.queryIntentActivities() for ACTION_MAIN + LAUNCHER. Found 0 records.
3 Activities have filter 3 separate app icons appear in App Drawer! Launcher creates a tile for every Activity declaring the filter, with its respective android:label.

Senior Android Interview Q&A Cheatsheet

Q1: What is the difference between singleTask and FLAG_ACTIVITY_CLEAR_TOP? ▼
Answer: singleTask is configured in the manifest and will always reuse the existing instance and deliver via onNewIntent().
In contrast, FLAG_ACTIVITY_CLEAR_TOP is an intent flag. If the target activity is configured with standard launch mode, CLEAR_TOP will destroy the target activity too and call onCreate() on a new instance, UNLESS combined with FLAG_ACTIVITY_SINGLE_TOP!
Q2: What is the exact lifecycle order when launching Activity B from Activity A? ▼
Answer:
1. A.onPause()
2. B.onCreate() → B.onStart() → B.onResume() (B is now interactive)
3. A.onStop()
Key point: A.onPause() MUST complete before B is created, which is why blocking work in onPause() causes sluggish transitions.
Q3: How does the OS decide whether to call onNewIntent() for singleTop? ▼
Answer: Inside system_server, ActivityTaskManagerService checks the focused task's child list: mChildren.last(). If top.component.equals(targetIntent.component) and launchMode == singleTop, it delivers the intent to deliverNewIntentLocked() without allocating a new ActivityRecord.
Q4: How do you implement a clean Logout flow that clears all screens? ▼
Answer:
val intent = Intent(context, LoginActivity::class.java).apply { flags = Intent.FLAG_ACTIVITY_NEW_TASK or Intent.FLAG_ACTIVITY_CLEAR_TASK } context.startActivity(intent)
