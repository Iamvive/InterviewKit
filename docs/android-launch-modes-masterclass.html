Tasks and the back stack

A task is a collection of activities that users interact with when performing a certain job. The activities are arranged in a stack—the back stack—in the order in which each activity is opened.

💡
Key Point
By default, all activities in the same application have an affinity for each other and run in the same task in a standard "Last In, First Out" (LIFO) back stack. Launch modes allow you to override this default behavior to create custom task hierarchies and navigation workflows.
Default LIFO Task Backstack Structure
Activity A (Root)
Activity B
Activity C

Pressing the Back button destroys Activity C and resumes Activity B.

Defining launch modes

Launch modes allow you to define how a new instance of an activity is associated with the current task. You can define launch modes in two ways:

  • Using the manifest file: Set the android:launchMode attribute in <activity>.
  • Using Intent flags: Pass flags such as FLAG_ACTIVITY_NEW_TASK or FLAG_ACTIVITY_CLEAR_TOP to startActivity().
Launch Mode Multiple Instances in Task? Separate Task? Can Host Other Activities?
standard Yes (always creates new) No (shares caller's task) Yes
singleTop Conditional (reused only if on top) No Yes
singleTask No (Root of its affinity task) Yes (if different affinity) Yes
singleInstance No (Only 1 instance system-wide) Yes (Always exclusive task) No (Always alone in task)
singleInstancePerTask No (Always root of its task) Yes (Can have multiple tasks) Yes

1. standard (Default)

The default mode. The system creates a new instance of the activity in the task from which it was started and routes the intent to it. The activity can be instantiated multiple times, each instance can belong to different tasks, and one task can have multiple instances.

AndroidManifest.xml XML 
<activity 
    android:name=".ActivityA"
    android:launchMode="standard" />

2. singleTop

If an instance of the activity already exists at the top of the current task, the system routes the intent to that instance through a call to its onNewIntent() method, rather than creating a new instance of the activity.

ℹ️
Behavior when not on top
If an instance of singleTop activity exists lower in the stack (not at the top), launching it creates a new instance on top of the stack.

3. singleTask

The system creates a new task and instantiates the activity at the root of the new task. However, if an instance of the activity already exists in an existing task with the same taskAffinity, the system brings that task to the foreground and delivers the intent via onNewIntent().

⚠️
The Clear-Top Side Effect
When a singleTask activity is brought to the foreground, all activities above it in that task are popped and destroyed (calling onDestroy()) to place the singleTask activity at the top!

4. singleInstance

Same as singleTask, except that the system does not launch any other activities into the task holding the instance. The activity is always the single and only member of its task; any activities started by it open in a separate task.

5. singleInstancePerTask API 31+

Introduced in Android 12 (API 31) for modern multi-window, foldable, and multi-document user experiences.

  • The activity can only run as the root activity of the task (the first activity that created the task).
  • Unlike singleInstance, this activity CAN launch other standard activities on top of itself inside the same task.
  • Unlike singleTask, multiple instances of this activity can exist across different tasks when combined with FLAG_ACTIVITY_MULTIPLE_TASK or FLAG_ACTIVITY_NEW_DOCUMENT.

The onNewIntent & setIntent Trap (Interview Gotcha)

When an activity is reused via singleTop, singleTask, or singleInstance, Android invokes onNewIntent(intent: Intent?).

🚨
Critical Rule: setIntent(intent) is Mandatory
getIntent() always returns the original Intent that launched the activity during its initial onCreate(). If you do not call setIntent(intent) inside onNewIntent(), any subsequent calls to getIntent() in onResume() or helper methods will read stale data!
MainActivity.kt Kotlin 
// ✅ Correct Implementation
override fun onNewIntent(intent: Intent) {
    super.onNewIntent(intent)
    setIntent(intent) // Updates the intent returned by getIntent()
    handleIntentExtras(intent)
}

Intent Flags Reference

Intent Flag Equivalent Launch Mode / Purpose Description
FLAG_ACTIVITY_NEW_TASK singleTask (Part 1) Starts activity in a new task according to taskAffinity.
FLAG_ACTIVITY_SINGLE_TOP singleTop Delivers to onNewIntent() if already at the top of stack.
FLAG_ACTIVITY_CLEAR_TOP singleTask (Part 2) Destroys all activities on top of target in the current task.
FLAG_ACTIVITY_CLEAR_TASK N/A Clears existing task completely before starting the root activity. Must be paired with FLAG_ACTIVITY_NEW_TASK.
FLAG_ACTIVITY_REORDER_TO_FRONT N/A Moves an existing activity from anywhere in the stack to the top without destroying intervening activities.

Task Affinity & Multi-Task Architectures

The taskAffinity attribute specifies which task an activity prefers to belong to. By default, all activities in an app have the same affinity (the package name).

💡
Case Study: Chucker / Network Inspector Architecture
Developer tools like Chucker use a custom android:taskAffinity="com.chucker.task" combined with FLAG_ACTIVITY_NEW_TASK and a separate category.LAUNCHER. This allows the debug UI to run side-by-side in Android's recent apps carousel without altering the main app's backstack!

ADB Dumpsys Diagnostics

To inspect real-time tasks and backstacks on connected hardware or emulators:

Terminal Bash 
# Print full activity hierarchy
adb shell dumpsys activity activities | grep -E "Task|Hist"

# Launch singleTask activity with intent flags
adb shell am start -n com.interview.kit/.launchmodes.ActivityC --activity-clear-top

Deep-Dive Doubts & OS Internal Mechanics

The following are in-depth technical explanations for real-world doubts and edge cases explored during practical testing.

⚙️
Doubt 1: How does the OS know which activity is on top to invoke onNewIntent vs onCreate?

When your app calls startActivity(intent), the call crosses an IPC Binder boundary to the system process: ActivityTaskManagerService (ATMS).

  1. In-Memory Hierarchy: ATMS maintains the system-wide RootWindowContainer → DisplayContent → TaskDisplayArea → Task → list of ActivityRecord objects.
  2. Top Evaluation: ATMS evaluates task.topRunningActivity(). If the target activity component name matches the current top ActivityRecord AND its launchMode is singleTop (or the intent contains FLAG_ACTIVITY_SINGLE_TOP):
  3. Binder Dispatch: Instead of constructing a new ActivityRecord and calling ApplicationThread.scheduleTransaction() for onCreate, ATMS dispatches a NewIntentItem transaction. The app's main thread receives this and executes activity.onNewIntent(intent).
📱
Doubt 2: Why was Activity D (singleInstance) hidden when going to background and tapping the App Icon?

When you have two separate tasks (Task 1: [A → B → A → B] and Task 2: [D (singleInstance)]):

  • Launcher Target: Your device's home screen launcher icon is mapped specifically to the root category.LAUNCHER activity (Task 1), launched with FLAG_ACTIVITY_NEW_TASK | FLAG_ACTIVITY_RESET_TASK_IF_NEEDED.
  • Foregrounding Primary Task: Tapping the launcher icon always brings Task 1 back to the foreground. Task 2 (Activity D) is not destroyed; it remains in the background.
  • How to access Task 2: To bring Activity D back, the user must either switch to it from the Android Overview / Recent Apps screen (where both tasks appear as separate cards if configured) or launch it via an explicit Intent!
🧹
Doubt 3: When does the OS destroy background tasks under memory pressure?

The OS kernel Low Memory Killer (LMK) and ATMS assign an oom_adj_score to processes.

  • Foreground Task process = Highest priority (least likely to be killed).
  • Background Task process = Cached/Empty priority (first to be reclaimed if system RAM runs low).
  • When a background task is trimmed, Android saves the view hierarchy state via onSaveInstanceState(). If the user returns later, the system recreates the task stack using the preserved bundle data.

Mock Interview Preparation (Staff / Senior Android)

Click on each scenario below to expand the architectural answers:

Q1: Deep Link notification arrives for a singleTask root activity

Scenario: App backstack is [MainActivity (singleTask)] -> [FeedActivity] -> [UserProfileActivity]. A push notification with PendingIntent launches MainActivity with new query params.

Behavior:

  1. Android identifies MainActivity exists in the task.
  2. FeedActivity and UserProfileActivity are popped and destroyed (calling onPause -> onStop -> onDestroy).
  3. MainActivity receives onNewIntent() -> onRestart() -> onStart() -> onResume().
  4. If setIntent(intent) is missing in onNewIntent, reading getIntent() in onResume() will return the old creation Intent instead of the notification parameters!
Q2: Launching startActivityForResult from a singleInstance activity

Scenario: A singleInstance activity calls startActivityForResult(cameraIntent, 100).

Behavior:

  • Because a singleInstance activity can never share its task with another activity, the target activity launches in a separate task.
  • On Android versions prior to Android 5.0 (API 21), onActivityResult() immediately returned RESULT_CANCELED without waiting!
  • Modern Android handles task cross-coupling for Activity Results, but standard practice is to use ActivityResultContracts or avoid singleInstance for interactive flows.
Q3: FLAG_ACTIVITY_CLEAR_TOP with standard vs singleTop

Scenario: Backstack has [A] -> [B] -> [C] -> [D] (all standard). From D, you launch B with FLAG_ACTIVITY_CLEAR_TOP.

Behavior:

  • C and D are destroyed.
  • Because B is standard, B is also destroyed and a completely new instance of B is created (calling onCreate())!
  • To reuse the existing B without recreating it, you must combine FLAG_ACTIVITY_CLEAR_TOP | FLAG_ACTIVITY_SINGLE_TOP.
